# Betting engine reference: odds loader, EV, confidence, parlay

Covers all six sports' fair-line evaluation stack: what's genuinely shared (imported directly, not duplicated) versus what's sport-specific and why. See [offline_data_contract.md](offline_data_contract.md) for the data-sourcing rules this engine follows, [college_sports_betting.md](college_sports_betting.md) for CFB/CBB's own architecture overview (including why their real data sources needed a different answer than NFL/NBA's), [mlb_pipeline.md](mlb_pipeline.md) / [nhl_pipeline.md](nhl_pipeline.md) for MLB/NHL's own overviews, [matchup_engine.md](matchup_engine.md) / [mlb_matchup_engine.md](mlb_matchup_engine.md) for the opponent-specific adjustment layers built on top of this one, and [ui_betting_tabs.md](ui_betting_tabs.md) for the seven pages that surface all of this.

## Why NFL, NBA, CFB, CBB, MLB, and NHL aren't one codebase

They share a *contract* (same shape of loader, same real-basis disclosure, same odds math, same `modules.unified_betting_contract` dispatch surface) but not a codebase. NFL's engine (`fantasy_engine/betting/`) was built first, is fully tested, and its prop model is a from-scratch Gaussian/Poisson fit on raw season rates. NBA already had a materially richer, pre-existing per-player model (`fuse_projection` + `get_reliability_score`, with minutes/pace/matchup/injury context) built for a different purpose (season-long fantasy projections) before any of this betting work started. Forcing NBA onto NFL's simpler prop model would have been a real quality regression, not just a style choice — so NBA's props are priced by wrapping its *existing* richer model, not by reimplementing NFL's. CFB, CBB, MLB, and NHL each had no such pre-existing rich model to wrap, so all four mirror NFL's from-scratch Gaussian/Poisson structure directly — see their own sections below.

What genuinely is shared: anything with no sport in it is imported directly, never copy-pasted. What isn't shared: anything that encodes a real, sport-specific fact (a scoring-margin constant, which stat categories overlap, which stats indicate a shared game script). This rule was applied identically as each new sport was added — no existing sport's file was refactored or touched to make room for the next one.

## Odds loader

| | NFL | NBA | CFB | CBB | MLB | NHL |
|---|---|---|---|---|---|---|
| Player props | `betting.odds_loader.unified_odds()` | `modules.nba_props_loader.unified_props()` | `modules.cfb_props_loader.unified_props()` | `modules.cbb_props_loader.unified_props()` | `modules.mlb_props_loader.unified_props()` | `modules.nhl_props_loader.unified_props()` |
| Game odds (moneyline/total) | same `unified_odds()` (games + props in one file) | `modules.nba_odds_loader.unified_game_odds()` (separate from props — see below) | `modules.cfb_odds_loader.unified_game_odds()` | `modules.cbb_odds_loader.unified_game_odds()` | `modules.mlb_odds_loader.unified_game_odds()` | `modules.nhl_odds_loader.unified_game_odds()` |
| Default file | `fantasy_engine/data/odds.json` (pre-generated, full week) | `data/nba_props.json` (pre-generated, season-long rates); `data/nba_game_odds.json` (empty — no fixed schedule to pre-populate) | `data/cfb_props.json` (empty by design — gated on `CFBD_API_KEY`, see [cfb_pipeline.md](cfb_pipeline.md)); `data/cfb_game_odds.json` (empty) | `data/cbb_props.json` (pre-generated this cycle — 484 real rows via ESPN's public API, see [cbb_pipeline.md](cbb_pipeline.md)); `data/cbb_game_odds.json` (empty) | `data/mlb_props.json` / `data/mlb_game_odds.json` (both empty by design — no live/keyless source this cycle, see [mlb_pipeline.md](mlb_pipeline.md)) | `data/nhl_props.json` / `data/nhl_game_odds.json` (both empty by design, see [nhl_pipeline.md](nhl_pipeline.md)) |
| Keying | `game_id`, `player_id:market` | `(player_name, category)`; games keyed by `away@home` matchup string (JSON-serializable form of the `(home, away)` pair) | same as NBA | same as NBA | same as NBA | same as NBA |

NBA/CFB/CBB/MLB/NHL game odds are all separate loaders from their own props (unlike NFL, which loads both from one file) because they have different lifetimes: props are season-long real per-game rates, stable enough to pre-generate once (where a real source exists); a specific day's/week's matchups aren't known far enough in advance to pre-generate the way a full NFL week is — see [nba_pipeline.md](nba_pipeline.md) / [cfb_pipeline.md](cfb_pipeline.md) / [cbb_pipeline.md](cbb_pipeline.md) / [mlb_pipeline.md](mlb_pipeline.md) / [nhl_pipeline.md](nhl_pipeline.md). MLB/NHL's game-odds schema also carries a `"total"` field, forward-compatible with a future total-runs/goals model — neither sport's moneyline model reads it yet.

## Unified dispatch layer: `modules/unified_betting_contract.py`

`load_odds(sport)`, `compute_ev(sport, props, **context)`, `compute_confidence(sport, priced_rows)`, `build_parlays(sport, legs)` — one call site and one output shape per function across all six sports, routing only, no new betting logic. `compute_ev("CFB", props)` does exactly what calling `modules.cfb_prop_model.evaluate_props(props)` directly already did. A uniform *output* does not mean a uniform *input*: NFL needs `players_by_id`, NBA needs `comparison_rows`, CFB and NHL need no extra context, CBB's `minutes_by_player` and MLB's `matchup_multipliers` are both optional — see the module's own docstring for exactly what each sport requires, [college_sports_betting.md](college_sports_betting.md) for CFB/CBB's full rationale, and [mlb_fusion_model.md](mlb_fusion_model.md) for what MLB's optional `matchup_multipliers` context is for. MLB and NHL's own richer overlay layers (MLB's season/matchup/fusion modules) are explicitly *not* part of this contract — see mlb_pipeline.md.

## EV engine

**Fully shared, not duplicated.** `betting.odds_math` — `american_to_decimal`, `implied_probability`, `remove_vig_two_way`, `expected_value`, `edge_vs_fair`, `fair_price_from_probability` — has no sport-specific content; it is American-odds math on numbers the caller supplies. `betting.prop_model`/`betting.moneyline_model` (NFL), `modules.nba_prop_model`/`modules.nba_moneyline_model` (NBA), `modules.cfb_prop_model`/`modules.cfb_moneyline_model` (CFB), `modules.cbb_prop_model`/`modules.cbb_moneyline_model` (CBB), `modules.mlb_prop_model`/`modules.mlb_moneyline_model` (MLB), and `modules.nhl_prop_model`/`modules.nhl_moneyline_model` (NHL) all import these functions directly from `fantasy_engine`'s `betting` package (importable from anywhere in this venv — see `fantasy_engine/pyproject.toml`'s editable install).

The one place NBA's EV computation genuinely differs: NBA props didn't originally carry over/under prices at all (`modules/nba_props_loader.py`'s row schema was extended to add `over_price`/`under_price`, defaulting to `-110.0` — same convention as NFL's `_DEFAULT_PRICE`), and NBA's probability distribution comes from `modules.nba_prop_model` treating `compare_props`'s existing `confidence_low`/`confidence_high` band as an approximate 90% interval rather than fitting a fresh Gaussian/Poisson model — see that module's docstring for why, and [offline_data_contract.md](offline_data_contract.md)'s rule 5 on disclosing the approximation.

CFB, CBB, MLB, and NHL have no pre-existing rich per-player projection system to wrap (NBA's `fuse_projection`/reliability infrastructure was built for fantasy basketball years before any betting work started; nothing analogous exists for any of the other three), so each mirrors NFL's from-scratch Gaussian/Poisson structure directly instead, priced from whatever real per-game rate a prop row's own `"line"` already carries:

- `modules.cfb_prop_model`/`modules.cbb_prop_model` model each rate as approximately **Gaussian**, with a single disclosed coefficient of variation. The one difference between the two: CBB has a real per-player `minutes`-per-game signal (from ESPN) that `modules.cbb_prop_model.minutes_volatility_multiplier` uses to widen the assumed variance for a low-minutes player; CFB has no equivalent live-verified per-player volatility source yet, so it uses one flat, wider constant (`_CFB_CV = 0.55` vs. CBB's `_BASE_CV = 0.35`) — see [cfb_pipeline.md](cfb_pipeline.md) / [cbb_pipeline.md](cbb_pipeline.md).
- `modules.mlb_prop_model` models every one of its 7 categories as **Poisson** instead — all are low-mean, non-negative per-game counts, the same shape `fantasy_engine/betting/prop_model.py`'s own NFL touchdown/reception markets already use Poisson for, and for the identical documented reason (a Gaussian badly understates a low-mean count's real spread). `modules.nhl_prop_model` splits its 4 categories across both families: goals/assists (low-mean counts) are Poisson, shots/saves (higher real mean) stay Gaussian with a disclosed CV — see [mlb_pipeline.md](mlb_pipeline.md) / [nhl_pipeline.md](nhl_pipeline.md).

## Confidence engine

**No new module was built for NBA — its existing, more sophisticated confidence infrastructure was reused instead of duplicated.** NFL's confidence is a simple inline blend in `betting.prop_model._confidence` (real-sample-size confidence, averaged with the ensemble's own confidence read). NBA already had `modules/reliability.py::get_reliability_score` (a full reliability model over recent variance, matchup difficulty, and injury impact) and `modules/props.py::prop_confidence` (confidence-band-width-based scoring) before this work started — both real signals, both richer than NFL's blend. `modules.nba_prop_model`'s priced rows pass through `compare_props`/`recommend_props`'s existing `confidence_score`/`reliability_score` fields unchanged; the parlay UI feeds `reliability_score / 100` in as each leg's `confidence`.

CFB, CBB, MLB, and NHL don't compute an explicit 0–1 confidence score at all — there's no richer model underneath to read one from, the way NBA has. Rather than leave the field blank or fabricate a number, `modules.unified_betting_contract.compute_confidence` maps their real, already-computed `risk_tier` (itself derived from a real coefficient of variation, via the same shared `_risk_tier` below) through a fixed, disclosed proxy table: `_RISK_TIER_CONFIDENCE_PROXY = {"low": 0.8, "medium": 0.5, "high": 0.25}`. This is a real function of an already-computed real classification, not an invented score — see the module's docstring. (MLB's optional `mlb_fusion_model.py` overlay computes its own richer per-category confidence, but that's outside this contract function — see [mlb_fusion_model.md](mlb_fusion_model.md).)

## Parlay engine

`betting.parlay_engine`'s leg construction, combined odds, correlation-adjusted probability math, and risk tiering (`make_leg`, `parlay_decimal_odds`, `correlation_adjusted_probability`, `_parlay_ev`, `_risk_tier`) are sport-agnostic and imported directly by every sport's own parlay engine, not duplicated. Only the *correlation pattern detector* has sport-specific content:

- **Reused unmodified for NBA/MLB/NHL:** the favorite/total pattern (`market == "moneyline"` correlating with `market == "total"`) — fully generic, fires for any sport's moneyline+total legs exactly as built for NFL.
- **NFL-only, doesn't apply to any other sport:** QB/pass-catcher stacks, RB volume+touchdown stacks (NFL stat-category sets).
- **NBA-only, new:** `modules.nba_parlay_engine.nba_detect_correlations` adds two NBA-specific patterns: same-player overlapping stat categories (a `PRA` leg structurally contains `points`/`rebounds`/`assists` — not independent), and same-team same-direction scoring stacks (two teammates' points legs, driven by the same game pace).
- **MLB-only, new:** `modules.mlb_parlay_engine.mlb_detect_correlations` adds four real baseball patterns — same-player HR/total-bases overlap (a home run is structurally 4 total bases), same-player hits/RBI, opposing-side pitcher-strikeouts-vs-high-strikeout-batter, and same-team teammate stolen-base environment. See [mlb_pipeline.md](mlb_pipeline.md).
- **NHL-only, new:** `modules.nhl_parlay_engine.nhl_detect_correlations` adds two real hockey patterns — same-player goals/assists overlap and same-team teammate goal stacks. See [nhl_pipeline.md](nhl_pipeline.md).

`modules.nba_parlay_engine.evaluate_parlay` calls `betting.parlay_engine.correlation_adjusted_probability(legs, correlations=nba_detect_correlations(legs))` — the generic engine's own top-level `evaluate_parlay` doesn't expose a way to inject a custom detector, so this is a thin thirty-line orchestration function, not a reimplementation of the underlying math. `modules.mlb_parlay_engine`/`modules.nhl_parlay_engine.evaluate_parlay` follow the identical shape.

**CFB and CBB needed no new correlation-pattern code at all.** Both `modules.cfb_parlay_engine` and `modules.cbb_parlay_engine` are thin re-exports — CFB re-exports `betting.parlay_engine` in full (identity-asserted by `tests/test_cfb_engine.py::CfbParlayEngineReExportTests`), CBB re-exports `modules.nba_parlay_engine` in full (same assertion in `test_cbb_engine.py`). The correlation phenomena themselves (a college QB and his pass-catcher share a real game script; a college guard's `PRA` structurally overlaps their own points/rebounds/assists) are the same real facts at the college level as the pro level — reusing the pattern *and* the code was correct, not a shortcut. **MLB and NHL are the opposite case** — baseball and hockey correlation patterns are genuinely new phenomena unrelated to any existing sport's, so both needed real new detector code rather than a re-export (see mlb_pipeline.md / nhl_pipeline.md). `modules/unified_parlay_engine.py`'s `detect_cross_sport_correlations` routes all six sports' legs to their own detector this way, partitioned by sport, so a CFB leg is never checked against a CBB leg (or any other cross-sport pair) — see [betting_engine_advanced.md](betting_engine_advanced.md) for the full cross-sport mechanism, extended across two build cycles from two sports to six.

## Team / moneyline model

Not shared, because the underlying facts genuinely differ: NBA scores are higher and more variable than NFL's, so NFL's published margin/total standard deviations (`NFL_MARGIN_STDEV = 13.5`, `NFL_TOTAL_STDEV = 10.0`) would be a real modeling error if reused for NBA. `modules.nba_team_model.real_margin_and_total_volatility` computes NBA's own standard deviations directly from this season's completed games (`margin_stdev`, `total_stdev` — see [nba_pipeline.md](nba_pipeline.md)) rather than assuming a published constant, which is more rigorous than the NFL side, not less.

CFB and CBB follow the identical pattern, with their own real, sport-specific fallback constants for when too few real games have been sampled yet: `modules.cfb_team_model.real_margin_and_total_volatility` falls back to `margin_stdev=21.0`/`total_stdev=17.0` (college football's much wider real talent gaps make both blowouts and upsets more common than the NFL's), and `modules.cbb_team_model.real_margin_and_total_volatility` falls back to `margin_stdev=12.0`/`total_stdev=11.5`. Every fallback is labeled `"basis": "fallback_estimate"`, never presented as if it were computed from real games — see [offline_data_contract.md](offline_data_contract.md) rule 5.

What *is* reused, by NBA/CFB/CBB: `betting.team_model.project_game` (the "your real scoring rate vs. opponent's real rate allowed" blend) takes no sport-specific constant at all — just team codes and an `averages` dict — so `modules.nba_moneyline_model.fair_moneyline`, `modules.cfb_moneyline_model.fair_moneyline`, and `modules.cbb_moneyline_model.fair_moneyline` all call it directly, each passing its own team model's `team_scoring_averages`/`build_team_scoring_averages` output (built to the identical `{"points_scored_avg", "points_allowed_avg", "games_played"}` shape NFL's `team_scoring_averages` already returns).

**MLB and NHL are the one place this pattern doesn't extend**, deliberately: `project_game` needs a real points-scored-average dict, and neither sport's engine fetches live scoring data this cycle (see mlb_pipeline.md / nhl_pipeline.md). `modules.mlb_moneyline_model.fair_moneyline` / `modules.nhl_moneyline_model.fair_moneyline` instead take a composite team rating built from caller-supplied context (pitcher/bullpen/park/defense/lineup for MLB; goaltending/offense/defense/special-teams for NHL, each defaulting to neutral `1.0` — no fabricated rating), converted to a win probability via a logistic transform of the rating difference plus each sport's own real, published home-field/home-ice win rate, rather than a normal approximation over a scoring margin neither sport has real data for here.
